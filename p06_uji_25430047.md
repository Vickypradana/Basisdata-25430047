## Detail Skenario dan Perintah SQL

### UJ-01 — Relasi pesanan dengan pelanggan

**Jenis:** Positif. **Acuan:** AB-01 dan foreign key pelanggan.

```sql
SELECT
    p.id_pesanan,
    p.id_pelanggan,
    pl.nama_pelanggan
FROM pesanan AS p
INNER JOIN pelanggan AS pl
    ON p.id_pelanggan = pl.id_pelanggan
ORDER BY p.id_pesanan
LIMIT 5;
```

**Hasil aktual:** Tampil 5 pesanan dengan pelanggan: (1, arep), (2, nia Ramadhani), (3, regina), (4, galeh Saputra), dan (5, alwann).  
**Analisis:** Kelima pesanan terhubung dengan pelanggan masing-masing.  
**Status:** Lulus.

### UJ-02 — Relasi detail pesanan dengan pesanan dan produk

**Jenis:** Positif. **Acuan:** Foreign key pada `detail_pesanan`.

```sql
SELECT
    dp.id_detail_pesanan,
    dp.id_pesanan,
    dp.kode_produk,
    pr.nama_produk
FROM detail_pesanan AS dp
INNER JOIN pesanan AS ps
    ON dp.id_pesanan = ps.id_pesanan
INNER JOIN produk AS pr
    ON dp.kode_produk = pr.kode_produk
ORDER BY dp.id_detail_pesanan
LIMIT 5;
```

**Hasil aktual:** Tampil 5 detail pesanan dan produk terkait: Lenovo LOQ 15, Monitor IPS 24 inci, PC Rakitan Ryzen 5, RAM DDR4 16 GB, dan Monitor IPS 24 inci.  
**Analisis:** Relasi detail-pesanan dan detail-produk berjalan sesuai harapan.  
**Status:** Lulus.

### UJ-03 — Perhitungan subtotal otomatis

**Jenis:** Positif. **Acuan:** Kolom `subtotal_detail` GENERATED.

```sql
SELECT
    id_detail_pesanan,
    jumlah_produk,
    harga_saat_pesanan,
    subtotal_detail,
    (jumlah_produk * harga_saat_pesanan) AS hasil_perhitungan
FROM detail_pesanan
ORDER BY id_detail_pesanan
LIMIT 5;
```

**Hasil aktual:** Lima subtotal sama dengan hasil perhitungan: Rp29.000.000, Rp1.850.000, Rp8.750.000, Rp650.000, dan Rp3.700.000.  
**Analisis:** Subtotal dihitung otomatis dari jumlah produk dikalikan harga saat pesanan.  
**Status:** Lulus.

### UJ-10 — Pesanan diproses sebelum pembayaran berhasil (utang desain)

**Jenis:** Uji aturan bisnis yang belum dijaga oleh constraint. **Acuan:** AB-04.

Pesanan 25 dipilih setelah query pencarian menunjukkan bahwa pembayaran pesanan tersebut berstatus `menunggu`.

```sql
START TRANSACTION;

UPDATE pesanan
SET status_pesanan = 'diproses'
WHERE id_pesanan = 25
  AND EXISTS (
      SELECT 1
      FROM pembayaran
      WHERE pembayaran.id_pesanan = pesanan.id_pesanan
        AND pembayaran.status_pembayaran = 'menunggu'
  );

SELECT
    ps.id_pesanan,
    ps.status_pesanan,
    pb.status_pembayaran
FROM pesanan AS ps
INNER JOIN pembayaran AS pb
    ON ps.id_pesanan = pb.id_pesanan
WHERE ps.id_pesanan = 25;

ROLLBACK;
```

**Hasil aktual:**
- UPDATE berhasil dan memengaruhi 1 baris.
- SELECT menampilkan ID pesanan 25, status pesanan `diproses`, dan status pembayaran `menunggu`.
- ROLLBACK berhasil dijalankan untuk membatalkan perubahan pengujian.

**Analisis:** Database mengizinkan pesanan diproses ketika pembayaran masih menunggu. Artinya, aturan AB-04 belum ditegakkan oleh constraint pada struktur database saat ini.  
**Status:** Pengujian berhasil membuktikan adanya celah aturan bisnis; AB-04 belum terlindungi.

## Kesimpulan

Sepuluh skenario pengujian telah dijalankan. Tiga pengujian positif membuktikan relasi dan perhitungan subtotal berjalan sesuai harapan. Enam pengujian negatif membuktikan constraint UNIQUE, CHECK, dan FOREIGN KEY menolak data tidak valid. UJ-10 membuktikan bahwa aturan AB-04 belum dijaga oleh struktur database.

## Utang Desain untuk Modul 14

**UD-01 — Penegakan AB-04 (pembayaran harus berhasil sebelum pesanan diproses).**

Tabel `pesanan` dan `pembayaran` belum memiliki mekanisme yang memastikan `status_pesanan` hanya dapat berubah menjadi `diproses` ketika `status_pembayaran` bernilai `berhasil`. UJ-10 membuktikan database menerima perubahan status pesanan 25 menjadi `diproses` saat pembayaran masih `menunggu`. Perubahan pengujian dibatalkan menggunakan `ROLLBACK`, sehingga data awal tetap terjaga.

Pada Modul 14, aturan ini perlu dijaga melalui mekanisme pemeriksaan logika bisnis, misalnya transaksi dan validasi sebelum status pesanan diubah.
